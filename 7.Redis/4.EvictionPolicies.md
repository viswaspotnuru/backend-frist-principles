When an in-memory cache like **Redis** or **Memcached** runs out of physical RAM, it cannot accept new data. To prevent a system crash, it triggers an **Eviction Policy**—a set of algorithms that automatically decides which old data to delete to make room for new incoming requests.

As a Senior Backend Architect, selecting the right eviction policy directly impacts your data integrity and latency. Here is a deep dive into the primary policies.

---

## 1. LRU: Least Recently Used (Age-Based)

The LRU policy assumes that data accessed recently will likely be accessed again soon. It tracks **when** a key was last requested.

```
[ Oldest Access / Eviction Candidate ] ---> [ Key A ] ---> [ Key B ] ---> [ Key C ] ---> [ Newest Access ]

```

* **The Mechanism:** Every time a key is read or updated, it moves to the top of the pile. When RAM fills up, the algorithm drops the keys at the very bottom—the ones that have sat idle the longest.
* **GoRestaurant Application:** This is perfect for **User Profiles** or **Active Orders**. Waiters are constantly updating active tables, so those stay in memory. Once a table pays and leaves, its data goes cold and is naturally evicted during the next rush.

---

## 2. LFU: Least Frequently Used (Popularity-Based)

The LFU policy assumes that highly popular data should stay cached, regardless of age. It tracks **how many times** a key has been requested.

```
Key Counters:  [ Key A: 2 hits ]  <-- Evict!     [ Key B: 45 hits ]     [ Key C: 120 hits ]

```

* **The Mechanism:** Every key has an internal counter. Every read operation increments that counter. When memory is full, the algorithm evicts the key with the lowest counter, even if it was just added a few minutes ago.
* **GoRestaurant Application:** This is ideal for your **Standard Menu Items**. A popular dish like a "Truffle Burger" gets thousands of hits a night and stays pinned in the cache, while an obscure seasonal item with only 2 hits gets safely cleared out.

---

## 3. TTL-Based Eviction (Time-to-Live / Volatile)

Instead of tracking user behavior (hits or age), this policy relies on a strict countdown timer assigned by the backend developer when writing the code.

* **The Mechanism:** In Redis, this is often configured as `volatile-ttl`. The system scans only the keys that have a set expiration time and evicts the ones whose clocks are closest to running out ($0$).
* **GoRestaurant Application:** Perfect for **External API Data** (like a weather API or third-party delivery service metrics) or **Temporary Promotion Codes** that are only valid for the next 30 minutes.

---

## 4. No Eviction (`noeviction`)

* **The Mechanism:** The cache completely refuses to delete anything automatically. When memory is full, any subsequent write command (`SET`, `HSET`, `LPUSH`) returns a system error (`OOM command not allowed when used memory > 'maxmemory'`). Read commands (`GET`) continue to work normally.
* **GoRestaurant Application:** Use this *only* if your Redis instance is operating as a **Primary Database** (e.g., storing critical financial transactions or session records that must never be lost). If this fills up, your frontend will see errors, but your data remains safe.

---

## Summary Matrix for System Design

| Policy | Metric Tracked | Eliminates | Risk Factor | Best Used For |
| --- | --- | --- | --- | --- |
| **LRU** | Time of last access | Old/stale data | Can evict a popular item if it goes cold for a brief period. | User sessions, active table states. |
| **LFU** | Cumulative hit count | Unpopular data | New items might get evicted instantly before they have a chance to gain "hits." | Menu catalogs, global configurations. |
| **TTL** | Expiration timestamp | Expired constants | If database updates happen faster than the TTL, you serve stale data. | Third-party API lookups, auth tokens. |
| **No Eviction** | Absolute memory limit | None (Throws error) | Will cause API write operations to fail during traffic spikes. | Critical data stores, message queues. |

---

### Senior Architectural Tip

In production systems like Redis, tracking a true, exact LRU across millions of keys requires too much CPU overhead. Instead, Redis uses a **recurrent randomized sampling algorithm (Approximated LRU)**. It picks a small sample of keys (e.g., 5 keys) and evicts the best candidate among that sample. As a senior developer, you can tune this accuracy in your configuration using the `maxmemory-samples` directive depending on your server's CPU capacity.
